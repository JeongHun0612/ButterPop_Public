## 촬영 방법

촬영일은 2026-10-14입니다. 현재 Unity 6000.4.5f1과 Recorder 5.1.6에서 작업했습니다.

1170×2532 H.264 MP4와 AAC 스테레오 오디오 출력은 실제 파일로 확인했습니다. Game View 입력에서는 검은 여백과 중복 화면이 나타나 최종 새 촬영본은 카메라의 Render Texture를 Recorder에 전달했습니다. 촬영 중 UI Canvas는 해당 카메라에 연결했습니다. 이 변경은 Play Mode의 촬영 상태에 적용했습니다.

플레이 조작은 실제 `Squish.Drop`, `ArmController.Raise/Lower` 경로를 호출했습니다. 안착·클리어 판정을 강제로 발생시키지 않았습니다. 새 촬영본에는 실패와 재시도도 포함되며, 실제 성공 연출은 프로젝트의 기존 녹화본을 함께 사용했습니다.

기존 녹화본은 1080×1920이며 현재 소스 이전의 UI가 보일 수 있습니다. 최종 영상에서는 원래 화면비를 유지해 배치했습니다. 기존 테스트 광고 표시는 실제 유료 결제나 운영 광고 검증을 의미하지 않습니다.

## 제작 도구의 편집·저장·재구성

실제 `StageMakerWindow`의 작업 데이터를 변경하고 프리뷰를 갱신했습니다. 저장은 동일 도구의 데이터 반영 메서드로 별도 임시 `StageDataSO`에 수행했으며, 이후 `StageBuilder`를 통해 그 데이터를 런타임에서 재구성한 장면을 촬영했습니다. 기존 스테이지 에셋을 덮어쓰지 않았습니다.

## 저장 검증

실제 `SaveService`와 검증용 메모리 Storage를 사용했습니다. 저장 요청 3개를 연속 예약하고 마지막 저장 완료를 기다린 경우 최대 동시 쓰기가 1개이고 기록한 진행도가 1 → 3 → 3인 것을 확인했습니다. 두 번째와 세 번째 요청은 실행 시점의 최신 데이터를 기록합니다.

로드 실패를 재현한 별도 인스턴스에서는 `IsReadOnly`가 유지되고 저장·삭제가 차단되는 것을 확인했습니다. 운영 파일 저장소를 사용하는 전체 장애 시험이나 실제 스토어·광고 SDK 검증을 수행한 것은 아닙니다.

첫 검증 시도에서는 같은 UniTask에 동시에 대기자를 붙이는 과정에서 continuation 등록 제약이 발생했습니다. 따라서 영상은 각 반환 작업을 동시에 기다리는 경우까지 검증했다고 주장하지 않으며, 위의 저장 요청 체인과 로드 실패 보호 범위만 보여줍니다.
